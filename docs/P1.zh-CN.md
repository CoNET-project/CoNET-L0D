# P1 — `web3://` 双向应用传输

对应英文版：[`P1.md`](P1.md)

修订：2026-08-22

公开指南：[Applications](https://gitbook.conet.network/applications/web3-url.html) ·
[Linux runtime](https://gitbook.conet.network/developers/conet-l0d.html)

## 1. 范围

P1 把钱包地址化目标转换为持续双向应用数据流。它服务于：

- Linux 服务器用 `--proxyDuplex` 发布本地 TCP 服务；
- Linux 客户端用 `--clientDuplex` 提供本地 endpoint；
- 浏览器与原生客户端实现同一 `web3://` session 协议。

本页描述应用传输，不重新定义公开 L1 节点加入方式，也不新增 SI 命令族。

## 2. Session 模型

```text
本地应用
   │
   ▼
web3:// runtime
   │  精确钱包目标 + 逻辑端口
   ▼
Entry A / Entry C ── CoNET L0 ── mailbox B
   │
   ▼
目标 runtime ── 本地 upstream
```

应用看到有序字节流；L0 提供加密路由与 line 投递。

| 步骤 | 机制 |
|---|---|
| 宣告可用 line | 已部署 SI 命令 `l0_listen` |
| 请求目标 line | 已部署 SI 命令 `l0_connect` |
| 协调 attachment | 应用消息 `duplex_offer` / `duplex_accept` |
| 拒绝 attachment | 应用消息 `duplex_reject` |
| 传输应用字节 | 已占用 line 上的 AES frame |
| 关闭 | socket close 与 `l0_pipe_end` |

`duplex_*` 是经现有 Chat/L0 路径承载的应用 framing，不是新的 SI 命令族。

## 3. Entry 与加密规则

| 对象 | 加密目标 | HTTP 目标 |
|---|---|---|
| 应用 offer | 目标 user PGP | 健康 Entry A，且 A 不得是 mailbox B |
| mailbox listen | 自身 mailbox route PGP | 健康 Entry C，且 C 不得是 mailbox B |
| line connect | 目标 mailbox route PGP | 健康 entry，再转发到 mailbox B |
| 应用数据 | 协商出的 session encryption | 已占用 L0 line |

HTTP 请求体始终只有：

```json
{ "data": "<OpenPGP armor>" }
```

任何控制值都不能作为明文同级字段加入。Entry 成功响应只证明入口已接受，不证明最终用户已收到。

## 4. 寻址

客户端形式：

```text
web3://<EOA>:<port>
web3://<ExactTag>.web3:<port>
```

示例：

```text
web3://0x1111111111111111111111111111111111111111:4200
web3://CoNET.web3:8080
```

Tag 必须精确且区分大小写。`CoNET.web3` 与 `CONET.web3` 可以对应不同钱包，
绝不能合并成搜索结果第一项。

## 5. Linux 服务器

```bash
conet-l0d start \
  --mainWallet 0x<main-paid-wallet> \
  --proxyDuplex 127.0.0.1:4200 \
  --config /etc/conet-l0d.toml
```

被发布应用继续绑定其正常本地地址。重启 runtime 不要求重启该应用。

多逻辑端口可以为每个 `[[l0.channels]]` 配置独立通信 EOA、通信 PGP key、
EIP-191 key、mailbox route key 与 listen-entry 集合。这与 SI exclusive occupancy
一致：一个 listen wallet 同一时间拥有一条 line。

## 6. Linux 客户端

```bash
conet-l0d start \
  --mainWallet 0x<main-paid-wallet> \
  --clientDuplex web3://0x<destination-wallet>:4200 \
  --config /etc/conet-l0d.toml
```

本地应用连接 `check-config`、`resolve` 或启动日志打印的 endpoint。runtime 随后：

1. 解析精确目标；
2. 选择该逻辑端口的 route；
3. 开启或复用 L0 line；
4. 保序双向转发字节；
5. 关闭时释放 line；
6. mailbox 返回临时冲突时采用有边界 backoff 重试。

## 7. 浏览器与原生客户端

浏览器/原生客户端无需 Linux 进程，直接使用同一目标与 session 语义。可移植实现需要：

- 精确 EOA 或 BeamioTag 解析；
- OpenPGP 与 EIP-191；
- 排除 mailbox B 的 Entry A / Entry C 选择；
- streaming HTTP/SSE，或具有同等语义的原生 bridge；
- 有序 duplex framing 与 close 处理；
- 请求失败时保留可信状态。

这是 Windows、macOS、Android、iOS 的主要客户端模型。

## 8. Fail-closed 行为

缺少必要 identity 或 routing material 时，runtime 不得开启 line。尤其：

- user key 不能替代 mailbox route key；
- outbound entry list 不能静默替代 listen-entry list；
- 通信 EOA 必须与其 EIP-191 私钥匹配；
- 两个逻辑 channel 不能共享 exclusive listen identity；
- 已占用 line 只属于当前 session generation；
- 过期 accept、reject、frame 或 end 消息不能修改新 session。

日志不得包含私钥、session key、明文 payload 或完整密文。

## 10. 研究证据

2026 年 8 月经授权的实验室运行，曾用 duplex transport 在 overlay endpoint
之间承载 geth 与 Prysm TCP 数据流：

- geth 在逻辑端口 `8400` 建立 peer；
- beacon 在逻辑端口 `4200` 建立 peer；
- consensus head 上升且 sync distance 下降；
- 只重启 `conet-l0d` 进程时，被发布应用保持运行；
- 持续 line conflict 或 queue saturation 仍是失败信号。

这些结果证明应用传输可互操作，不证明公开 CoNET L1 节点已经从公网 P2P 切到 L0。

## 11. 验收门

应用 profile 只有满足以下条件才算 P1 通过：

1. 目标钱包与端口无歧义；
2. server 经现有 mailbox 路径收到 offer；
3. 双方对同一个当前 session generation 达成一致；
4. 有序字节可双向流动；
5. close 可释放 endpoint 与 mailbox ownership；
6. 无需重启被发布应用即可 reconnect；
7. 日志中无 secret material；
8. entry 失败或畸形数据不会覆盖可信状态。

## 12. 范围外

- 新 SI `p2p_stream_*` 命令；
- 仅为 L1 发明新的 `listenKind`；
- 修改公开 L1 加入路径；
- 把浏览器支持描述成 Linux daemon port；
- 从本 TCP duplex profile 承诺通用 UDP 行为。

## SI 池传输选择
启用时，P1 控制 POST、listen 与占用 L0 pipe 优先使用 GuardianNodesInfoV6 SI 池；失败候选会冷却，静态 SI entries 仍是关闭池时的显式回退。
